# Work plan: SP-6 / SP-4-R / SP-5 — handoff package for the GB10 agent

Dated plan for active work (doc lifecycle applies). Handoff target: the twoFour agent
(`apollo11@172.30.30.24`), which has the repo, the verified exllamav3 1.6.1 env
(`~/.venvs/exl3sc`), and the tank mount. Owner split is explicit per package; the
strategic context lives in `docs/maintainer/2026-10-12-fork-strategy.md` (SP-4/5/6 rows).

**Operating rules for every package (from the W2.5 lesson):**

- **Producer-side status.** The process that runs writes its own state to a
  `state.log` in its package directory on the tank (`/nfs/ninfer-gb10/<pkg>/state.log`)
  at every phase transition and on exit. No remote polling; a reader never wonders
  whether something is still running.
- **Single GPU instance per box.** Trueno's 32 GiB is a shared pool (29 GiB resident);
  the GB10's unified pool is dedicated but still one job at a time.
- **Handoff trail.** Each package closes with a README (outcome, verified coverage,
  exact commands) + SHA256SUMS for artifacts + a beads `cws` entry, matching the
  W2.3/W2.5 culture.

## SP-6 — GB10 native 125B bring-up (primary; GB10 lane, twoFour)

**Goal (strategy SP-6 row):** the Qwen3.8 Flash-Next 125B-A6B serves on the GB10
natively — demand paging, no streaming code — and the resident-set and PLE
demand-paging behavior are measured.

**Prerequisites (discover first, report if missing):**

1. The 125B Flash-Next artifact. Check `/nfs/hub` and the tank for an existing
   `.ninfer` (the PLE file-mapped form is the existing disk tier per the strategy).
   If absent, the conversion is its own sub-task: the BF16 source checkpoint
   (`/nfs/models--Qwen--Qwen3.8-27B` is the 27B — the 125B source is a different
   model; locate `Qwen3.8-Flash-Next-125B-A6B` on the HF cache or flag it), the
   converter route `qwen3_8_flash_next_125b_a6b` (`tools/convert/`), and the GB10's
   disk budget. Do not start a multi-hour conversion without the owner confirming
   the source.
2. The serving binary for `sm_121a`. The repo's default build targets `sm_120a`;
   cross-compile with `-DCMAKE_CUDA_ARCHITECTURES=121a` on the GB10 (the attribution
   tool already does this pattern) or build natively there.

**Steps:**

1. Stage the artifact + the serving binary + the state.log in
   `/nfs/ninfer-gb10/sp6-bringup/`.
2. Launch the serve with the deployment-representative flags (the 27B pool's flag
   line adapted: the KV capacity per the artifact's geometry, `--spec mtp` if the
   artifact carries the MTP head, `--no-vision` unless the vision components are
   bound). Log the exact command in the README.
3. Measure: the resident set at startup (the GPU memory + the unified-pool
   breakdown), the PLE demand-paging behavior under load (the page-ins on the
   cold expert access — the `ninfer_` metrics' tier-traffic and context-transfer
   series expose it), the decode/prefill saturation via
   `tools/bench/run_serve_concurrency.py --mode mtp0 --suite decode-saturation`
   at C=1/2/4/8, and the 27B baseline comparison rows where applicable.
4. Acceptance (the strategy row): the 125B serves on the GB10 natively; the
   resident-set and the PLE demand-paging behavior are measured and written into
   the package README + the plan.

**Owner:** twoFour executes; the requestor supplies any missing artifact and
reviews the numbers.

## SP-5-R — n+2 layer-ahead prefetch refinement (scoped low; after SP-4-R)

**The plan's own scoping:** the value exists only on the 125B bring-up (SP-6); on
the 35B stand-in the product path runs a full tail (zero misses) and the forced-limit

numbers decide whether SP-5-R is worth a window at all.

**Steps (when justified):** the prefetch depth n+2 in the device-side adaptation

their layer consumes them is the failure mode); measure at the 26/52, 13/52, and
