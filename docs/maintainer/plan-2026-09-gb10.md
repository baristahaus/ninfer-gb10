# GB10 plan — September 2026

Temporary working plan for the GB10 (`sm_121a`) fork. Remove it when the work below is finished
or abandoned; stable results move into `docs/performance/qwen3.8-flash-next-125b-a6b.md` and the
affected references.

Steps 0–3 need the GB10 and are scripted under `tools/gb10/`. Run them on the GB10, then share
one generated report; nothing needs to be copied by hand. Steps 4–7 are code changes that use
those results.

## Quick start on the GB10

```bash
git clone https://github.com/baristahaus/ninfer-gb10.git && cd ninfer-gb10   # or: git pull
cp tools/gb10/config.example.sh tools/gb10/config.local.sh
$EDITOR tools/gb10/config.local.sh      # set ART to the .ninfer path; set SERVE_ARGS to your flags
uv tool install git+https://github.com/SeraphimSerapis/tool-eval-bench.git   # for step 1

tools/gb10/step0_build_test.sh          # build + tests                  (~build time)
tools/gb10/step1_json_check.sh          # JSON streaming fix + TEB TC-64..69 (~10 min)
tools/gb10/step2_baseline.sh            # bandwidth + unprofiled baseline (~30–60 min)
tools/gb10/step3_attribution.sh         # nsys attribution + PLE faults  (~20–40 min)
tools/gb10/report.sh                    # joins the summaries
```

Then share `profiles/bench/gb10/report.md` (a few KB of Markdown). Each script prints its own
summary as it finishes and keeps raw logs beside it under `profiles/bench/gb10/stepN/` (ignored
by git); only open those if a summary points at a failure.

Notes:

- Run the steps in order; each one stops with a clear message if its prerequisite is missing.
  Step 0 must be green before the others mean anything.
- Steps 1 and 2 start and stop their own temporary server on `PORT`; stop your normal server
  first if it uses the GPU memory the benchmarks need.
- Steps 2 and 3 are timing runs: keep the machine otherwise idle.
- `nvcc` is taken from `PATH`, else `/usr/local/cuda/bin/nvcc`; set `NVCC=` to override.
- Step 3 needs Nsight Systems (`nsys`) on `PATH`. It builds a separate annotated copy in
  `build-trace/`, so `build/` stays the clean timing build.
- The serving matrix in step 2 is off by default (about an hour, and it needs `transformers`
  for its prompt fixture). Enable it with `RUN_SERVING=1` and `TOKENIZER=` in the config.

## Why the order below

Only the routed experts are NVFP4 in the Flash-Next artifact. Everything else is BF16. From the
binding shapes in `src/models/qwen3_8_flash_next_125b_a6b/impl/load_plan.cpp`, one decode token
at T=1 reads approximately:

| Weights | Bytes per token |
|---|---:|
| GDN projections, 36 layers (qkv, z, out) | ~4.2 GB |
| Full attention, 12 layers (q, k, v, o, indexer) | ~1.2 GB |
| HyperConnection, two per layer | ~1.3 GB |
| `lm_head` (248320 × 2560) | ~1.3 GB |
| Router and shared expert | ~0.6 GB |
| Routed experts, NVFP4 (10 of 512 per layer) | ~1.3 GB |

About 9.9 GB per token, 13% of it NVFP4. At GB10's 273 GB/s theoretical LPDDR5X bandwidth the
MTP0 decode ceiling is roughly 27 tokens/s. These are estimates; step 2 measures them. Tuning the
existing NVFP4 kernels can recover at most part of that 13%; converting dense projections to
NVFP4 is where the headroom is, but it changes the artifact and model quality, so it comes last.

Two memory facts matter on GB10's 128 GB unified memory: routed experts are about 68 GB of
device weights, and the PLE table is a 51 GB FP8 file mapped from disk and gathered on the CPU.
Together they do not fit alongside the BF16 weights, KV and workspaces, so cold PLE rows may be
read from disk during decode (step 3).

## 0. Build and correctness — `step0_build_test.sh`

Configures `build/` for `sm_121a` with tests and benchmarks and trace annotations off, builds,
runs the full `ctest` suite, then the Flash-Next real-artifact tests
(`ninfer_qwen3_8_flash_next_(real|load_plan|frontend)_test`) against `ART`. The summary lists
pass/skip/fail counts, failing test names and the tail of any failing output.

Decision: any failure is fixed before the later steps are run.

## 1. JSON streaming fix and TEB structured output — `step1_json_check.sh`

Starts a temporary server with `SERVE_ARGS`, then sends a streamed and a non-streamed
`json_schema` request that ask for a fenced answer, and a streamed `json_object` request that
asks for prose around a fence. For each it checks: no error event, `[DONE]` present, exactly
one content delta, and content that is bare, valid JSON. It then runs `tool-eval-bench probe`
and scenarios TC-64..TC-69 (`--seed 42`) if tool-eval-bench is installed.

Decision: a streamed FAIL is a regression of the merged fix; TEB transport errors on these
scenarios point at the serving layer rather than the model.

## 2. Unprofiled baseline — `step2_baseline.sh`

The only valid basis for later speed claims. Measures sustained memory bandwidth with
`tools/hbm_bandwidth_probe.cu`, warms the page cache, then runs `ninfer_bench` with 8K and
64K prompts and 512 decode outputs (`--max-ctx 73728 --prefill-chunk 8192`, `KV_DTYPE`, one
warmup and five measured repetitions) for MTP off, MTP with `DRAFT_TOKENS`, and MTP3 (both
with the optimized proposal head). The summary tabulates prefill and decode tokens/s (mean ± sd)
and mean accepted length. With `RUN_SERVING=1` it also runs `run_flash_next_serving.py` on a
server started with `--no-prefix-reuse`.

Afterwards, a GB10 section with these numbers goes into
`docs/performance/qwen3.8-flash-next-125b-a6b.md`.

## 3. Where decode time goes — `step3_attribution.sh`

Builds an annotated `ninfer_bench` in `build-trace/`, captures Nsight Systems traces at an 8K
prompt with 32 decode outputs for MTP off and MTP with `DRAFT_TOKENS`, and attributes GPU work
per stage with `tools/bench/flash_next_performance.py` against
`tools/bench/hardware/gb10.json`. That profile uses NVIDIA's 273 GB/s; its compute rates are
derived (dense NVFP4 as half the 1 PFLOP sparse rating, BF16 as NVFP4/4, FP32 31 TFLOPS), which
matters for prefill estimates but hardly for bandwidth-bound decode. Replace them if NVIDIA
publishes dense GB10 rates. The step finishes with a decode run on the clean build that counts
system-wide major page faults and records `free -g` before and after, for PLE residency.

Decisions:
- Decode achieves well below the bandwidth ceiling in a stage → that stage is a kernel target
  (steps 5–6) before any artifact change.
- PLE gather or major faults are material → fix residency first (e.g. `mlock` the table, or
  smaller KV/workspace budgets); it is cheaper than any kernel work.
- BF16 stages dominate and already run near bandwidth → only step 7 moves decode materially.

## 4. `tool_choice: required` — real enforcement or honest rejection

Today `required` is a system-prompt instruction. TEB's probe (`probe_tool_choice_required`)
tells the model "Do not call any tools" and reports the endpoint as *enforcing* if a call
arrives anyway, so a prompt-guided pass makes TC-45 results incomparable with backends that
constrain decoding. Choose one:

- **Enforce with a forced token (preferred).** The Frontend already forces a control span when
  the thinking budget runs out (`OutputSession::preview_control`,
  `src/models/qwen3_8_flash_next/impl/frontend/frontend.cpp`; Engine side
  `append_forced_tokens` in `src/runtime/engine/engine_core.h`). Extend the output session so
  that, for a required tool choice, the first answer token after `</think>` (or the first
  token when thinking is off) is forced to `<tool_call>`. Named choice forces
  `<tool_call>\n<function=NAME>\n`, which also allows Anthropic `{"type":"tool"}`; Anthropic
  `{"type":"any"}` maps to required. Forcing `{` at the same point is a cheap partial
  enforcement for JSON `response_format`. The requirement must travel from `serve` through
  `ninfer::PromptInput` options to both families' output sessions; read the thinking-budget
  path end to end first, since it defines when the Engine asks for control tokens.
- **Or reject `required` again** until the above exists; TEB then excludes TC-45 and the score
  stays comparable.

With either choice, remove the tool-call instruction from `to_prompt_input` and move the JSON
instruction from the folded leading system block to a trailing text part of the last user
message. The leading block currently changes whenever `response_format` or `tool_choice`
differs between turns — TEB does both — so every such turn re-prefills the whole conversation.
Verify: serving schema tests, TEB probe output (`tool-eval-bench probe`), TEB `--short` and
`--hardmode --trials 5 --seed 42`, and the prefix-cache hit count on follow-up turns in the
request log.

## 5. SM count ownership and GB10 launch constants

Replace the `device_sm_count()` global (`src/ops/common/device_info.*`) with the existing
`ExecutionContext::multiprocessor_count` (from `DeviceContext`) at each call site: RMSNorm,
RoPE, GDN chunked output, QSA scores, Flash-Next MoE, sparse-MoE prefill. Then measure each
constant on GB10 instead of scaling it — the values today are 5090/PRO 6000 tunings multiplied
by the SM ratio, and the RMSNorm cut-off was an empirical 5090 crossover. Also run the RTX PRO
6000 once if available: the fork changed its MoE grid from 510 to 564 blocks unmeasured.

Evidence: the affected op tests, a per-op microbenchmark sweep at the Flash-Next shapes, then the
step 2 benchmark. Keep a change only if the end-to-end result meets the repository gate (at least
2% faster with a positive 95% interval where claimed, no single-request regression above 2%).

## 6. NVFP4 routed-expert decode on 48 SMs

Scope: `run_nvfp4_decode_routes` in `src/ops/sparse_moe/flash_next/flash_next_moe.cu`.

- Launch geometry at T=1: about 50 gate-up blocks and 200 down blocks today; sweep rows per
  block and split along K so every SM streams weights.
- Fuse activation quantize → gate-up (SwiGLU) → down → weighted reduce into fewer launches.
- T = 3–6 (MTP verify, two lanes): more distinct experts per layer; check whether grouped routes
  beat per-assignment routes on GB10.

Evidence: `ninfer_flash_next_moe_test` (independent oracle) at the real shapes, op-level timing,
then step 2.

## 7. Dense projections to NVFP4 (major change)

Only after step 3 confirms the BF16 byte share. Order by bytes read: GDN qkv/z/out, `lm_head`,
HyperConnection up/down, attention q/o, shared expert. Needs a converter recipe change under
`tools/convert`, 2560-wide NVFP4 decode/small-T ops (the existing NVFP4 input-projection ops are
shaped for Qwen3.5's 5120), and binder changes in the 125B-A6B package. Quality gate: fixed-token
scores against the BF16-projection artifact (`ninfer-perplexity --token-scores`, see
`docs/perplexity.md`) plus TEB `--hardmode --trials 5 --seed 42` against the current
89.2 ± 0.4. Speed gate: step 2.
