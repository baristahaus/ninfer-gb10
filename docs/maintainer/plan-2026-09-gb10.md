# GB10 plan — September 2026

Temporary working plan for the GB10 (`sm_121a`) fork. Remove it when the work below is finished
or abandoned; stable results move into `docs/performance/qwen3.8-flash-next-125b-a6b.md` and the
affected references.

Steps 0–3 need the GB10 and are scripted under `tools/gb10/`. Run them on the GB10, then share
one generated report; nothing needs to be copied by hand. Steps 4–7 are code changes that use
those results.

## Quick start on the GB10

```bash
git clone https://github.com/baristahaus/ninfer-gb10.git && cd ninfer-gb10   # or: git pull
cp tools/gb10/config.example.sh tools/gb10/config.local.sh
$EDITOR tools/gb10/config.local.sh      # set ART to the .ninfer path; set SERVE_ARGS to your flags
uv tool install git+https://github.com/SeraphimSerapis/tool-eval-bench.git   # for step 1

tools/gb10/step0_build_test.sh          # build + tests                  (~build time)
tools/gb10/step1_json_check.sh          # JSON streaming fix + TEB TC-64..69 (~10 min)
tools/gb10/step2_baseline.sh            # bandwidth + unprofiled baseline (~30–60 min)
tools/gb10/step3_attribution.sh         # nsys attribution + PLE faults  (~20–40 min)
tools/gb10/probe_memory.sh              # unified-memory probe; weight samples if ART is set (~15 s)
tools/gb10/report.sh                    # joins the summaries
```

Then share `profiles/bench/gb10/report.md` (a few KB of Markdown). Each script prints its own
summary as it finishes and keeps raw logs beside it under `profiles/bench/gb10/stepN/` (ignored
by git); only open those if a summary points at a failure.

Notes:

- Run the steps in order; each one stops with a clear message if its prerequisite is missing.
  Step 0 must be green before the others mean anything.
- Steps 1 and 2 start and stop their own temporary server on `PORT`; stop your normal server
  first if it uses the GPU memory the benchmarks need.
- Steps 2 and 3 are timing runs: keep the machine otherwise idle.
- `nvcc` is taken from `PATH`, else `/usr/local/cuda/bin/nvcc`; set `NVCC=` to override.
- Step 3 needs Nsight Systems (`nsys`) on `PATH`. It builds a separate annotated copy in
  `build-trace/`, so `build/` stays the clean timing build.
- The serving matrix in step 2 is off by default (about an hour, and it needs `transformers`
  for its prompt fixture). Enable it with `RUN_SERVING=1` and `TOKENIZER=` in the config.

## Why the order below

Only the routed experts are NVFP4 in the Flash-Next artifact. Everything else is BF16. From the
binding shapes in `src/models/qwen3_8_flash_next_125b_a6b/impl/load_plan.cpp`, one decode token
at T=1 reads approximately:

| Weights | Bytes per token |
|---|---:|
| GDN projections, 36 layers (qkv, z, out) | ~4.2 GB |
| Full attention, 12 layers (q, k, v, o, indexer) | ~1.2 GB |
| HyperConnection, two per layer | ~1.3 GB |
| `lm_head` (248320 × 2560) | ~1.3 GB |
| Router and shared expert | ~0.6 GB |
| Routed experts, NVFP4 (10 of 512 per layer) | ~1.3 GB |

About 9.9 GB per token, 13% of it NVFP4. The memory probe measured 246 GB/s of GPU streaming
read on GB10 (NVIDIA's specification is 273 GB/s), so the MTP0 decode ceiling is about
25 tokens/s. Other engines already sit there: llama.cpp reaches 24.5 tokens/s and DGPP 24.3 with
the dense weights in BF16 (reference points below). With the dense weights in FP8 the read drops
to about 5.6 GB and the ceiling rises to about 44 tokens/s; DGPP reaches 32.7 there.

NInfer measured 19.3 tokens/s without speculation (51.8 ms per token, step 2), 78% of the
ceiling, where those two engines run at about 98%. Step 3 places about 5 ms of the 12 ms gap in
the NVFP4 routed experts and the HyperConnection combine; the rest is in the smaller stages and
between kernels. Prefill (1,514 tokens/s at 8K) is already ahead of the other GB10 engines, and
the PLE table does not fault once it is page-cached (step 3). The order is therefore:

1. step 7a, FP8 dense weights: the largest measured gain on this hardware (DGPP 24.3 → 32.7
   tokens/s without speculation, the same model and NVFP4 experts), and it raises the ceiling
   every later kernel step works against;
2. step 6, the NVFP4 routed-expert decode route (`moe.nvfp4`, 76% of its bandwidth estimate)
   and the HyperConnection combine (71%), then L2 weight prefetch;
3. step 5's launch constants and the prefill stages step 3 flags (`qsa.select` at 6.9% of its
   estimate, `gdn.prefill` and `hyper.combine_mix` at about 13%).

Step 4 (`tool_choice: required`) is independent of these and can run alongside.

## 0. Build and correctness — `step0_build_test.sh`

Configures `build/` for `sm_121a` with tests and benchmarks and trace annotations off, builds,
runs the full `ctest` suite, then the Flash-Next real-artifact tests
(`ninfer_qwen3_8_flash_next_(real|load_plan|frontend)_test`) against `ART`. The summary lists
pass/skip/fail counts, failing test names and the tail of any failing output.

Decision: any failure is fixed before the later steps are run.

## 1. JSON streaming fix and TEB structured output — `step1_json_check.sh`

Starts a temporary server with `SERVE_ARGS`, then sends a streamed and a non-streamed
`json_schema` request that ask for a fenced answer, and a streamed `json_object` request that
asks for prose around a fence. For each it checks: no error event, `[DONE]` present, exactly
one content delta, and content that is bare, valid JSON. It then runs `tool-eval-bench probe`
and scenarios TC-64..TC-69 (`--seed 42`) if tool-eval-bench is installed.

Decision: a streamed FAIL is a regression of the merged fix; TEB transport errors on these
scenarios point at the serving layer rather than the model.

Result, 2026-09-27: all three JSON checks pass. TEB TC-64..TC-69 scores 83/100: TC-68 (schema
violation resistance, no `response_format` in the request) fails 0/2 in three runs because the
model wraps its JSON in prose. That is model behavior the serving layer must not rewrite
without a requested format; step 4's forced `{` covers only requests that ask for JSON.

## 2. Unprofiled baseline — `step2_baseline.sh`

The only valid basis for later speed claims. Measures sustained memory bandwidth with
`tools/hbm_bandwidth_probe.cu`, warms the page cache, then runs `ninfer_bench` with 8K and
64K prompts and 512 decode outputs (`--max-ctx 73728 --prefill-chunk 8192`, `KV_DTYPE`, one
warmup and five measured repetitions) for MTP off, MTP with `DRAFT_TOKENS`, and MTP3 (both
with the optimized proposal head). The summary tabulates prefill and decode tokens/s (mean ± sd)
and mean accepted length. With `RUN_SERVING=1` it also runs `run_flash_next_serving.py` on a
server started with `--no-prefix-reuse`.

GPU telemetry (added 2026-09-28): after the timing runs, one decode-dominated run per
configuration (1K prompt, 1536 outputs, 1 warmup + 2 measured) runs under `nvidia-smi`
sampling every 0.5 s (utilization, power draw, SM clock, temperature), plus 10 s idle. The
summary reports, over the window between the first and last sample at ≥ 50% utilization
(model load excluded): utilization mean, power mean/p95/peak, SM clock mean/min, and joules per
output token (mean power over decode tokens/s, prefill included in the window at about 1-3%).
Read together: utilization near 100% means no host gaps between kernels, not full SMs; a
minimum SM clock falling below the ~2450 MHz seen at 41 W means decode has become partly
power-bound, and kernel choices then have to weigh energy as well as bytes. The one earlier
sample (BF16 artifact, K=2, pre-sync): 41.2 W mean, 55.5 W peak, SM clock 2405–2489 MHz,
about 0.9 J per token; btop on twoFour now shows about 96% utilization and 77 W and more under
FP8 serving, which this measurement puts on a comparable footing.

The same table carries effective bandwidth: modeled bytes per emitted token
(`tools/gb10/decode_bytes.py`, read from the artifact directory: dense weights in full, routed
experts at 10/512 per token or their uniform-routing union over an MTP round's K+1 tokens, the
GDN state read and written, the MTP draft steps; QSA KV/indexer and activations excluded) times
decode tokens/s, against the in-run probe. From the inventory the model gives 10.2 GB per
token for the BF16 artifact and 6.6 GB for FP8 without speculation, and 3.4 GB per token for
FP8 at K=2 with the bench corpus's 2.99 tokens per round. Applied to the post-sync step 2 rows:
BF16 208 GB/s (84% of 246), FP8 197 GB/s (80%), FP8 K=2 196 GB/s (80%). Every configuration
sits at the same fraction of the memory wall; speculation raises tokens per byte, not bytes per
second, and the remaining ~20% is the latency-bound small-kernel time of step 6.

Every row above is greedy, the best case for MTP: a sampled token agrees with the draft less
often than an argmax does, so the bench corpus's 2.99 tokens per round at K=2 overstates served
speed. Step 2 therefore repeats the 8K rows for MTP off and `DRAFT_TOKENS` with
`ninfer_bench --sampling model --seed 1`, the model's registered sampling preset (what a served
request gets by default; `docs/performance/methodology.md` publishes stochastic numbers the same
way). The gap between the greedy and sampled K rows is the speculative gain real traffic loses;
the MTP-off pair shows the sampler's own cost.

Afterwards, a GB10 section with these numbers goes into
`docs/performance/qwen3.8-flash-next-125b-a6b.md`.

Result, 2026-09-27 (fp8 KV, 1 warmup + 5 measured, in-run bandwidth probe 247 GB/s):

| Speculation | Prefill 8K / 64K tokens/s | Decode 8K / 64K tokens/s | Mean accepted |
|---|---:|---:|---:|
| none | 1,514 / 1,473 | 19.3 / 19.1 | — |
| MTP K=2 | 1,435 / 1,400 | 44.6 / 43.6 | 2.99 / 2.98 |
| MTP K=3 | 1,435 / 1,398 | 52.0 / 51.1 | 3.96 / 3.96 |

Decode and prefill barely change from 8K to 64K. The MTP rows are an upper bound: the bench
corpus (`bench/fixtures/qwen3_8_flash_next_context.ids`) is curated text tiled to length, and
the model's continuation of it accepts almost every draft (3.96 of 4 at K=3; upstream records
100% at 8K on the same corpus). A K=3 round costs 76 ms against 51.8 ms for a plain step, so at
the 56–88% per-token acceptance other engines report on real prompts (2.0–3.3 tokens per
round), K=3 lands at about 27–44 tokens/s. The serving matrix (`RUN_SERVING=1`) or TEB's
acceptance counters give the real figure; claims about speculative decode use those, not these
rows. Real-text figure, 2026-09-28 (`step7a_baseline.sh`, 16 corpus streams × 1,024 greedy
tokens, BF16-projection artifact): 64.8% of drafted tokens accepted.

After step 6 item 1 (yield synchronize on GB10), same configuration, in-run bandwidth probe
244 GB/s: decode 19.6 / 19.4 without speculation (+1.6%), 45.7 / 44.4 at K=2 (+2.5% / +1.8%) and
53.7 / 52.4 at K=3 (+3.3% / +2.5%). These are the current baseline.

Result, 2026-09-28 (BF16 artifact, `2add6bb2`, in-run probe 232 GB/s): decode 20.2 / 19.8,
44.2 / 42.9 (2.99/2.98 accepted), 52.0 / 50.6 (3.96/3.96) tok/s; prefill 1,528 / 1,488 — within

SM 2469, 71 °C, 20.0 tok/s, 1.59 J per output token, 10.18 GB/token modeled, 203 GB/s (88% of

K=3: 38.8 W (51.4 peak), SM 2468 (floor 2405), 72 °C, 35.7 tok/s, 1.09 J/token, 208 GB/s (90%).
The MTP rows carry a caveat: the 1K-prompt power runs decode a less-predictable region of the
bench corpus — effective draft acceptance ≈ 70% at K=2 and ≈ 57% at K=3 against the ~99% of the
8K timing runs (the 7a corpus average over 16 windows is 65.9%) — so their 35.4/35.7 tok/s is a
realistic-acceptance operating point, not a regression against 44.2/52.0, and their J/token is
energy per emitted token at that acceptance, wasted drafts included; their effective GB/s uses
the full-acceptance byte model and is not a clean bandwidth fraction. The K=0 row is the clean
one: 1.59 J/token, 203 GB/s = 88% of the probe, clocks steady at 2469 with a 71 °C ceiling.

Result, 2026-09-28 (FP8 artifact, `3ea1ad13`, in-run probe 232 GB/s): decode 29.8 / 28.9,
56.8 / 55.5 (2.99/2.98 accepted), 65.5 / 63.4 (3.96/3.96) tok/s; prefill 2,449 / 2,342 — within
run-to-run variance of the §9.3 post-sync FP8 row. Same telemetry pattern, one step hotter:
K=0 35.2 W (51.3 peak), SM 2467 (floor 2392), 74 °C, 29.4 tok/s, 1.20 J per output token,
194 GB/s (83% of the probe); K=2 39.6 W (53.9 peak), 76 °C, 42.6 tok/s, 0.93 J/token,
198 GB/s (85%); K=3 41.0 W (53.5 peak), SM 2464, 42.1 tok/s, 0.97 J/token, 203 GB/s (87%);
idle 8.4 W. The MTP rows carry the same low-acceptance caveat as the BF16 set (effective
draft acceptance ≈ 62% / 52% — again near the 65.9% corpus average, so their J/token is
energy per emitted token at realistic acceptance, wasted drafts included). At K=0 against
the BF16 set: FP8 decodes 1.47× faster (29.4 vs 19.95 tok/s) at 1.11× the power — 1.20 vs
1.59 J per output token, a ~24% energy saving per emitted token.

Operational note: a run that reads more than the page cache can hold (the file-page probe's
125 GiB evictor) leaves the cache full, and model load then fails the free-device-memory check.
Drop the page cache (`echo 3 > /proc/sys/vm/drop_caches`) before a benchmark that follows it.

## 3. Where decode time goes — `step3_attribution.sh`

Builds an annotated `ninfer_bench` in `build-trace/`, captures Nsight Systems traces at an 8K
prompt with 32 decode outputs for MTP off and MTP with `DRAFT_TOKENS`, and attributes GPU work
per stage with `tools/bench/flash_next_performance.py` against
`tools/bench/hardware/gb10.json`. That profile uses the probe's measured 246 GB/s; its compute rates are
derived (dense NVFP4 as half the 1 PFLOP sparse rating, BF16 as NVFP4/4, FP32 31 TFLOPS), which
matters for prefill estimates but hardly for bandwidth-bound decode. Replace them if NVIDIA
publishes dense GB10 rates. The step finishes with a decode run on the clean build that counts
system-wide major page faults and records `free -g` before and after, for PLE residency.

Decisions:
- Decode achieves well below the bandwidth ceiling in a stage → that stage is a kernel target
  (steps 5–6) before any artifact change.
- PLE gather or major faults are material → fix residency first; it is cheaper than any
  kernel work. Options, cheapest first: smaller KV/workspace budgets or `mlock`; the INT4 PLE
  table of step 7a (30 GB instead of 51 GB); reading only the 16 rows a token needs, either with
  batched `O_DIRECT` reads into private staging (giveen/ninfer-ext `cbeb294b`,
  `--ngram-residency stream`) or into a fixed device buffer before the forward pass so decode
  CUDA Graphs stay intact (tonyd2wild's single-Spark vLLM recipe).
- BF16 stages dominate and already run near bandwidth → only step 7 moves decode materially.

Result, 2026-09-27 (8K prompt, 32 decode outputs, 97.5–97.8% of GPU work attributed). MTP off,
one decode round (one token) in the traced run:

| Decode work | ms per round | Estimate ms | Gap ms |
|---|---:|---:|---:|
| `gdn.update` | 18.64 | 17.87 | 0.76 |
| `moe.nvfp4` (router, shared and routed experts) | 10.25 | 7.83 | 2.42 |
| `hyper.combine_mix` | 7.10 | 5.06 | 2.04 |
| `qsa.select`, 12 layers at 8.2K context | 6.47 | 5.02 | 1.45 |
| `ple.update`, `hyper.mix`, `hyper.combine`, `hyper.repeat` | 0.53 | 0.43 | 0.10 |
| Unattributed GPU work (matches `lm_head`: 1.27 GB is 5.17 ms at 246 GB/s) | 5.36 | — | — |
| GPU idle | 4.66 | — | — |
| Total | 53.0 | | |

The traced round is 53.0 ms against 51.8 ms untraced (step 2). The unattributed work and the idle
time are assigned to decode because the report's decode phase shares already include the
unattributed time and prefill is one 8192-token chunk. The QSA estimate covers its projections
only; the missing scoring work makes its real gap smaller than 1.45 ms, not larger.

Recoverable per round: about 5.2 ms in kernels (the NVFP4 expert route 2.4, the HyperConnection
combine 2.0, GDN 0.8), at most 1.5 ms in QSA, and up to 4.7 ms of idle time. Recovering all of it
reaches about 42 ms (24 tokens/s), where llama.cpp and DGPP already are; beyond that only fewer
bytes (step 7) help.

With MTP K=2 the decode shares become `moe.nvfp4` 30.2%, `gdn.record` 28.5% (94.3%),
`hyper.combine_mix` 11.5% and `qsa.select` 10.8% (71.7%); the MTP predictor is about 3.5%. In
prefill, `gdn.prefill` takes about 37% at 13% of its estimate, `hyper.combine_mix` about 21% at
14%, `qsa.select` about 20% at 6.9% (843 GFLOP, the largest inefficiency in the trace) and
`moe.nvfp4` about 16%. The host PLE gather costs 9.2 µs per warm decode round (NVTX median;
72 ms when its pages are cold); the report's 4.4 ms over 33 calls includes the prefill gather.

Decisions taken:
- the GDN stages are at bandwidth; the NVFP4 experts and the HyperConnection combine are the
  kernel targets (step 6);
- idle time, located on the existing traces (kernel gaps bucketed by length):
  - MTP off used to run every kernel eager: `layouts_impl.h` disabled ordinary Flash-Next
    graphs because their replay "corrupts continuation state after the first decode step"
    (lkarlslund `d397c4a8`; still so on lkarlslund/ninfer master and absent from
    Neroued/ninfer, which has no Flash-Next family). About 1,375 launches per token at ~2.2 µs
    cost about 3 ms per token, so the MTP-off row of step 2 carries launch overhead that the
    graph-based engines it is compared with do not. Cause (found by mtdphn): the ordinary
    decode entry binds no valid-column tensor, so the layer loop filled one from a heap
    `std::vector` with a pageable host-to-device copy. Eager execution stages that copy before
    the vector is freed; a captured graph keeps the freed address and every replay reads
    recycled memory. The copy is now a device-side `fill_i32` and ordinary graphs are on again.
    Verified on twoFour 2026-09-28: `test_engine_real` passes on both artifacts with the
    ordinary path now graphed (its ordinary greedy check compares against the checkpoint
    output; the per-recipe goldens held), and the MTP-off rows gain 2.5–2.7 ms per token
    (19.6/19.4 → 20.7/20.4 and 28.2/27.4 → 30.3/29.5 tok/s at 8K/64K);
  - MTP K=2 (the served configuration) runs 85% of its kernels in graphs, and 90% of its idle
    time is between rounds: the round's graph ends with the egress copy to the host
    (`mtp_impl.h`), the host reads the accepted tokens, the speculative commit tail launches
    the round's GDN/PLE replay folds and blocks a second time, then the host hashes and
    gathers PLE rows, writes the ingress and launches the next round. Excluding two long
    outliers at verify-input preparation, the GPU was idle about 4.4 ms per round before the
    yield change (below), roughly 6% of the 71 ms round;
- the between-round gap, attributed (49 decode gaps over 200 µs in
  `step3-pre-yield/mtp2.sqlite`, the pre-instrumentation trace; each gap's next kernel matched
  to its launch call by correlation id): 43 are the GPU waiting for the host, and the suspected
  mid-round synchronize (22 of the 43, bucketed between `qsa.select`
  and GDN) does not exist: every one of those gaps is a round boundary. The round's graph
  (1,498 kernels) ends with the final QSA layer's `shortlist_exact_select` plus the egress
  copy, and the round's eager tail starts with the GDN replay fold, so bucketing by adjacent
  kernel names straddles the boundary; in each sampled gap the previous kernel correlates to
  `cudaGraphLaunch` and the next to `cudaLaunchKernel`, and no host readback happens
  mid-round. There are two blocking synchronizes per round, not one: `decode.mtp.wait` after
  the round's graph, and the speculative commit tail (`resolve_pending_raw`,
  `program_impl.h`) which launches the eager tail — GDN `recurrent_fold` (~958 µs) and PLE
  `ple_fold` (~14 µs) — and blocks again. The host's own work between the two syncs and the
  next launch is 30–110 µs (egress read and validation ~31 µs; ingress with PLE hash and
  gather ~68 µs in the anchor round; 7.7 KB of ingress). The rest is two costs:
  - each synchronize returns 1.2–2.4 ms (medians ~1.98 ms and ~1.4 ms in the anchor window;
    262–2935 µs across the run) after the GPU finished. The engine set
    `cudaDeviceScheduleBlockingSync` (`src/core/device.cu`, upstream `4c0fe48a`, 2026-09-22,
    to stop the Engine thread spinning a core), so both syncs sleep and are woken by the
    driver; on GB10 that wake-up, likely including CPU idle-state exit, appears to cost about
    1.4 ms per wait;
  - `cudaGraphLaunch` of the verify graph takes 909–1966 µs in the pre-yield trace, and its
    first kernel starts about 750 µs after the call begins; item 2 below shows this is the
    trace's per-node instrumentation, not the engine. Anchor-round idle (pre-yield), 4.4 ms ≈ 6% of the 71 ms
    round: sync wake-ups 3.4 ms, fold GPU 1.0 ms, graph launch ~0.9 ms, host work ~0.1 ms.

  `tools/gb10/probe_sync.sh` measured both without the engine or a profiler:
  - blocking synchronize returns 401 / 670 / 956 / 1181 µs (p50) after kernels of 50 µs, 1 ms,
    10 ms and 60 ms; yield, spin and auto return in 2.7–2.8 µs at every duration. Pinning the
    thread to an A725 or an X925 core does not change blocking's order of magnitude;
  - a graph of 100, 1,000 or 4,000 empty kernels launches in 1.6–14 µs and starts its first
    kernel within 14.5 µs, so launch cost does not scale with node count on GB10. The ~950 µs
    in the trace comes from the capture itself (`--cuda-graph-trace=node` instruments every
    node) or per-round graph updates, which item 2 below instruments;
- step 6 starts with that gap, in this order:
  1. the wake-up, done: `src/core/device.cu` uses `cudaDeviceScheduleYield` on integrated
     devices and keeps blocking on discrete GPUs. Yield busy-waits with `sched_yield`, but decode
     is 1.6–3.3% faster (step 2) and the GPU clock stays at 2405–2489 MHz through a K=2 decode
     (41 W mean, 56 W peak), so the busy host core costs no GPU clock under the shared budget;
  2. the remaining host path, done: NVTX sub-ranges inside `decode.mtp.submit` —
     `decode.mtp.submit.graph` around the graph profile install, `decode.mtp.submit.ingress`
     around the per-row ingress loop including per-round KV reservation
     (`materialize_sequence_kv`) and the host PLE hash and gather, and
     `decode.mtp.egress` around the post-sync egress read; `cuda_graph.launch` and
     `decode.mtp.wait` cover the launch and the first synchronize. The commit tail's folds and
     second synchronize are covered by the execution-timing recorder's own `program.submit` /
     `device.wait` / `program.post` ranges — a dedicated range spanning them is
     unrepresentable: the tail alternates the recorder's NVTX phases, and each transition
     pops the recorder's range below an outer one, corrupting the pairing (the trial range
     measured 0.1–0.4 µs around a 982 µs synchronize and was removed). The suspected
     mid-round synchronize is settled: it does not exist — the 22 `qsa.select`→GDN gaps are
     the round boundary (above). Post-yield re-capture (8K prompt, 32 outputs, 26 decode
     rounds): the first sync returns 10–24 µs after the round's last kernel (pre-yield
     262–2935 µs); the egress read is 0.2–0.8 µs on unified memory; the ingress is 6–11 µs
     when the PLE rows are page-resident, up to 8.1 ms on the 3 of 26 rounds whose
     continuation rows fault; the profile install is 0.1–410 µs (16 µs mean, the spikes are
     profile switches); and `cudaGraphLaunch` runs 609–1000 µs in every round of the
     node-traced build — uniform, no per-round update spike, 1.6–14 µs in the clean-build
     probe, so it is the `--cuda-graph-trace=node` instrumentation. The round is GPU-bound
     (65.0–66.6 ms graph + 0.98 ms eager fold, unchanged), 43.95 output tokens/s traced,
     45.7 untraced (step 2 A/B).

     With the yield change the round boundary is no longer a host problem: warm, the host
     spends about 0.1 ms per 67 ms round (two ~20 µs synchronizes, egress, ingress, launch),
     well under 1%. What remains at the boundary is the eager GDN `recurrent_fold` (~0.98 ms of
     GPU work, about 1.5% of the round) and PLE rows that fault on the host (3 of 26 rounds in
     this capture, up to 8.1 ms each). The fold reads and writes every GDN layer's FP32 state,
     so it is bandwidth work that stays; running it inside the graph tail from the
     device-known accepted count would remove only its eager launch and second synchronize.
     Step 6's remaining gains are therefore GPU work: the NVFP4 expert route and the
     HyperConnection combine (step 6 kernel list), after step 7a.
  3. the PLE hash and gather on the device, only if cold PLE rows stall rounds in steady
     serving (count major faults during a served session, not after a page-cache eviction);
     launching round N+1 without the host is no longer worth the Engine contract change
     described below, since the warm boundary now costs under 1%. The
     file-page probe (`tools/gb10/probe_file_pages.sh`) settles feasibility: a kernel reads
     page-cached rows of a file mapping at 162–169 GB/s (about 30% below device memory,
     irrelevant for a 7.7 KB gather) and survives cold pages, which fault in parallel at about
     1 µs per row amortized (96 µs for one serial fault) with no errors or hangs. Warm, this
     saves only ~11 µs per round; its value is the cold tail (the host gather's 72 ms outliers)
     and taking the host out of the next round's inputs. The hash depends on the previous two
     tokens and the segment position, which resets at EOS (`ple_table.cpp`), so on the device
     it is per-sequence state computed for draft tokens and rolled back to the last accepted
     token: part of the MTP accept/commit state. It stays in `src/models/qwen3_8_flash_next`
     (file-backed PLE), with the host implementation as its exact oracle, bit for bit across
     EOS resets and partial acceptance. Launching round N+1 before the host reads round N
     changes the Engine's round-boundary contract (`docs/maintainer/engine-architecture.md`):
     a round launched after the request ends must leave GDN state, KV and the output
     transaction untouched.

  Each item is gated on a re-capture of step 3's MTP K=2 trace (gap buckets and NVTX medians)
  and a step 2 re-run against the current baseline (45.7 tokens/s at K=2), with fixed-prompt
  greedy output identical to the build before the change. Programmatic dependent launch (knoopx `e0a6d18c`) targets only the
  in-round gaps left in the graphs (about 20 ms per run) and the eager kernels around them; it
  comes after these;
- PLE residency is settled: 0 major page faults over 147 s once the table is page-cached, and the
  host gather is negligible. The table stays file-backed; none of the residency options above
  is needed.

## Memory probe — `probe_memory.sh`

A standalone CUDA program (`tools/gb10/memory_probe.cu`, needs no model or config) that measures
the unified-memory questions driver source cannot settle on this machine. With `ART` set in the
environment or `config.local.sh`, `tools/gb10/weight_samples.py` first copies 64 MiB of each
decode-path weight class out of the artifact (BF16 GDN, HyperConnection and `lm_head`, NVFP4
experts, the FP8 PLE table, the Q4 proposal head), and the probe repeats the compression
comparison on those bytes (section 2b).

1. what CUDA reports: `integrated`, `pageableMemoryAccess`,
   `pageableMemoryAccessUsesHostPageTables`, `concurrentManagedAccess`, host-native atomics, and
   the driver's generic-compression support;
2. whether `cuMemCreate` grants generic ("compute data") compression, and whether a granted
   allocation reads zero-filled data faster than a plain one (random data should not change);
3. GPU read bandwidth from `cudaMalloc`, from pinned host memory and from plain `malloc` memory
   read in place, plus host-to-device copy rates;
4. CPU-only read bandwidth, GPU-only read bandwidth, and both at once.

Decisions:
- `malloc` memory read in place near `cudaMalloc` speed → zero-copy PLE gather and zero-copy
  staging instead of host-to-device copies (step 3);
- compression granted and faster on zero-filled data → test KV cache and activation buffers with
  it; no difference → drop the idea;
- a large drop in GPU bandwidth while the CPU reads → keep host-side work (PLE, grammar masks,
  drafting) off the decode path's bandwidth.

Two runs, 2026-09-27 (idle GB10, CUDA 13.0.88, driver 580.173.02, 1 GiB buffers). First run:

| Measurement | GB/s |
|---|---:|
| GPU read, `cudaMalloc` or plain `cuMemCreate` | 245–246 |
| GPU read, compression granted, zero-filled | 2068 |
| GPU read, compression granted, random data | 245.7 |
| GPU read in place, pinned host / `malloc` memory | 174 / 161 |
| Host-to-device copy, payload | 59 |
| CPU read alone, 20 threads | 136 |
| GPU + CPU reading together | 241 total (GPU 177) |

The second run, with `ART` set, read plain memory at 236–240 GB/s (about 3% below the first),
pinned host memory in place at 216 GB/s, and found compression gains of 1.00–1.01× in section 2b
on every weight class: BF16 GDN, HyperConnection and `lm_head`, NVFP4 experts, the FP8 PLE table
and the Q4 proposal head.

Readings:
- 246 GB/s is the decode ceiling; `tools/bench/hardware/gb10.json` uses it.
- Generic compression is closed: it pays only for data that is zero or constant in a block, and
  real weight bytes read no faster (section 2b). Live KV is not compressible either, and
  attention never reads KV padding.
- Weights stay in device allocations: host memory read in place reaches 71–91% of device speed
  across the two runs. For host-resident data (PLE rows, host replicas) reading in place is still
  about 3× faster than a host-to-device copy.
- CPU and GPU share one budget: GPU and CPU together read no more than the GPU alone. CPU
  memory traffic during decode (PLE page-cache misses, tokenizer or server work, other
  processes) comes out of decode bandwidth, so benchmarks run on an otherwise idle machine.

## 4. `tool_choice: required` — real enforcement or honest rejection

Today `required` is a system-prompt instruction. TEB's probe (`probe_tool_choice_required`)
tells the model "Do not call any tools" and reports the endpoint as *enforcing* if a call
arrives anyway, so a prompt-guided pass makes TC-45 results incomparable with backends that
constrain decoding. Choose one:

- **Constrained decoding (strongest).** igorls/ninfer (`bb7b7305`, `2cbdb2b6`) compiles JSON
  Schema and EBNF grammars with xgrammar into per-request token masks
  (`src/runtime/contract/structured_output.{h,cpp}` there: `OutputConstraintCompiler`,
  `OutputConstraintState` with `next_mask`/`accept`/`fork`) and keeps MTP drafting on under a
  constraint. That covers `tool_choice: required` and named choice and turns `json_schema` into a
  guarantee, which TEB TC-64..TC-69 score. It is written against the pre-v3 `src/targets`
  layout, so it is a port: the mask applies in both families' sampling and speculative-verify
  paths, and the vendored xgrammar build must work with CUDA 13.0 on GB10.
- **Enforce with a forced token (preferred).** The Frontend already forces a control span when
  the thinking budget runs out (`OutputSession::preview_control`,
  `src/models/qwen3_8_flash_next/impl/frontend/frontend.cpp`; Engine side
  `append_forced_tokens` in `src/runtime/engine/engine_core.h`). Extend the output session so
  that, for a required tool choice, the first answer token after `</think>` (or the first
  token when thinking is off) is forced to `<tool_call>`. Named choice forces
  `<tool_call>\n<function=NAME>\n`, which also allows Anthropic `{"type":"tool"}`; Anthropic
  `{"type":"any"}` maps to required. Forcing `{` at the same point is a cheap partial
  enforcement for JSON `response_format`. The requirement must travel from `serve` through
  `ninfer::PromptInput` options to both families' output sessions; read the thinking-budget
  path end to end first, since it defines when the Engine asks for control tokens.
- **Or reject `required` again** until the above exists; TEB then excludes TC-45 and the score
  stays comparable.

With either choice, remove the tool-call instruction from `to_prompt_input` and move the JSON
instruction from the folded leading system block to a trailing text part of the last user
message. The leading block currently changes whenever `response_format` or `tool_choice`
differs between turns — TEB does both — so every such turn re-prefills the whole conversation.
Verify: serving schema tests, TEB probe output (`tool-eval-bench probe`), TEB `--short` plus
one `--hardmode --seed 42` trial, and the prefix-cache hit count on follow-up turns in the request
log.

Status (2026-09-28, `ed0f08e4`): the placement part is done — the directive is a
trailing text part on the final turn, so turns that only change `response_format`
or `tool_choice` no longer re-prefill (TEB multi-turn prefix-cache hit count
91.9% → 92.5%, worklog 9.3). Enforcement of `required` itself is still
prompt-only: no constrained decoding or forced-token path exists, so TC-45
comparability stays prompt-guided until one of the two enforcement options above
is implemented.

`hyper.combine_mix` gap (measured on the fp8proj artifact, step 3 mtp2, T=3): ~56 µs per
call against the 27.7 µs useful-bytes estimate — 49.6%, a 28–29 µs gap, the second-largest
absolute decode gap after `moe.nvfp4` (the 7a second pass initially dropped the hyper stages
from this list; retracted, the gap is not small). It splits about evenly: ~14 µs is the two
small-grid elementwise kernels (`combine_grouped_rmsnorm` 10.6 µs at grid 4×T,
`gate_mix_injection_decode` 5.9 µs at grid 14×T, against ~2.1 µs of modeled bytes — serialized
launch and DRAM latency on 48 SMs) and ~14 µs is the FP8 projection pair (down + SiLU 21.1 µs
at grid 20, up 18.9 µs at grid 2) at about two-thirds of the estimate's 246 GB/s. At T=1 the
stage runs at 54.8% of its estimate, the elementwise pair 65% of the gap, the GEMV pair at
77%. The lever is structural, not bytes (7a already cut 10.07 → 6.81 MB per call): a fused
T≤4 hyper-mix kernel — rmsnorm → FP8 down + SiLU → FP8 up → gate/injection in one launch, the
whole stage being 6.8 MB of weights and 0.3 MB of activations at T≤4 — the GB10 ordering of
the group-norm-fusion and batched-decode ports above, targeting the elementwise/latency share
first and the projection bandwidth as a second pass. Evidence: `ninfer_hyperconnection_test`,
per-kernel timing, then step 2.

L2 weight prefetch: DGPP (HawkBearPig/dgpp, `src/kernels/l2_prefetch.cu`) reads upcoming
weight windows into the 24 MB L2 on a low-priority side stream while the decode chain runs
latency-bound work (norms, routing, small kernels), so the consuming GEMVs then read at 347–630
GB/s. Disabling it cost 8% per decode step on their four-node GLM-5.3. Keep the in-flight window
small: 3 MB in flight made every memory access on the box wait about 12 µs; their light
setting keeps 128 KB in flight and the full one 768 KB. It helps only while a step is chain-bound rather than bandwidth-bound, which step 3 shows
per stage. In NInfer it is an Op-owned prefetch node in the decode graph, sized per stage.

MTP draft head: tonyd2wild's vLLM recipe drafts over the 65,536 lowest token ids only and keeps
64% acceptance (3.56 tokens per step) with full-vocabulary verification. Our optimized proposal
head has 147,456 rows and is read at every draft step; a smaller head is a byte cut to measure
against acceptance.

Evidence: the independent op oracles at the real shapes (`ninfer_flash_next_moe_test` and the
HyperConnection/PLE/QSA suites), op-level timing, then step 2.

### 7c. Lossless 12-bit BF16 for what stays BF16

DGPP's `bf16_weights: "bf12"` stores each BF16 weight as its sign-and-mantissa byte plus a 4-bit
exponent code, with exact side tables for the rare exponents outside the code range; the GEMV
rebuilds the exact BF16 bits in registers. Output is bit-identical from 25% fewer bytes: +6–12%
single-stream decode on their GLM models and Flash-Next FP8. For us it applies to whatever step
7a leaves in BF16 (embedding and HyperConnection at least, `lm_head` if it stays BF16). It is
a new registered tensor format (`docs/maintainer/tensor-formats.md`) with a converter-side
encoder and an exact codec oracle, not a quantization: the quality gate is bit-identical
decoded weights, so only the speed gate applies.

### 9.1 Engine OOM recovery vs the failure contract — TRUE (highest risk)

`bb41fdf2` (ported from gzenz/ninfer `3f3272d6`, cherry-picked from `93165378`; matches the
review's provenance note) catches `std::bad_alloc` **and** `std::logic_error` in the worker
loop and runs `recover_from_oom_locked` (`engine_core.h:2115-2171`): it errors the
active/materializing requests, resets the scheduler and the Program
(`fail_all_cleanup`, `program_impl.h:9483` — noexcept and best-effort:
`clear_lane_best_effort`, `release_*_best_effort`, `(void)release_shared_prefix`), and leaves
the pending FIFO to retry, bounded by `kOomMaxRecoveries` (8) consecutive recoveries, beyond
which it fails all. Contract §7.4 (`engine-architecture.md:545-555`) says the opposite: after
a GPU mutation where neither commit nor a stable abort can be formed the whole Engine must
fail, and internal invariant errors must not degrade into a retry. The 30+ `logic_error`
throw sites in `engine_core.h` are all internal invariant checks. `fail_all_cleanup` can
partially fail without any completeness check, and the retry path then executes against the
result. No test covers the path (the `tests/` bad_alloc hits are allocator-layer simulations).
Present mitigations: the narrow admission-window catch (`engine_core.h:1655`, request-local
failure, no retry), the consecutive-recovery bound, hard fail when the waiting request is
lost, cleanup under `execution_mutex_`.

Fix (her two options combined — narrow where the contract is unambiguous, document where the
code is operationally right):

- `logic_error` in the worker loop → `fail_all_locked`, unconditionally. Drop the
  "recoverable logic error (e.g. stale checkpoint state image)" branch: no throw site
  characterizes a logic_error as transient checkpoint state, and invariant errors failing the
  Engine is exactly what §7.4 requires.
- `bad_alloc` → keep the recovery (transient allocation failure is an operational reality on
  unified memory; the admission window is already scoped) but make it all-or-nothing:
  1. drain the compute stream before cleanup — the failing unit's in-flight round kernels
     must complete before lanes are invalidated and their pool pages released;
  2. after `fail_all_cleanup` + `clear_after_program_cleanup`, verify the Program is quiescent
     (new `noexcept` introspection: no active context transaction, no live continuation or
     shared-prefix slots); any residue → `fail_all_locked`. The cleanup stops being an
     assumption and becomes a check.
- Contract: add the failure taxonomy to `engine-architecture.md` §7.4 — a transient
  allocation failure with a drained, verified clean rollback is a recoverable event (bounded
  by the consecutive cap); invariant violations and unverifiable cleanups fail the Engine.
- Test: a test-only fault-injection seam (throw `bad_alloc` from the materialization
  reserve) asserting (a) single OOM → the affected request fails with a retryable error,
  the pending FIFO still completes, the Engine stays alive; (b) more than the cap of
  consecutive OOMs → fail-all of the pending FIFO; (c) an injected invariant error →
  immediate Engine failure with no recovery.

## EXL3 — evaluated, not adopted (2026-09-27)

ExLlamaV3's Flash-Next pack `3.05bpw_h5_ng5` (turboderp; about 80 GB) on one Spark, from
[vcruz305's recipe](https://github.com/vcruz305/Qwen3.8-Flash-Next-EXL3-DGX-Spark-recipe):
33 tok/s without drafting; with MTP depth 5 and dynamic stopping 79 on code (73% acceptance),
62 on DevOps text, 53 on prose. The 4.05 bpw pack is slower (30 without drafting).

Bytes per token, from ExLlamaV3's allocation code (`conversion/allocation.py`,
`architecture/qwen4_exp.py`): experts 3 bpw, GDN 4–5, attention and shared expert 5, head 5,
router FP16, and the HyperConnection mixers 16-bit because the quantizer has no rule for them
(1.27 GB per token; vcruz's int8 mixer option recovers +4–7 tok/s). About 4.2–4.5 GB per token,
not the 2.7 GB estimated earlier from "3 bits everywhere". After all of step 7 NInfer reads about
4.4 GB: NVFP4 experts at 4.5 bpw cost 0.44 GB more than 3-bit trellis experts, FP8
HyperConnection weights 0.6 GB less than 16-bit mixers.

Decision: no EXL3 tensor format. Its remaining byte advantage is about 10%, and it would need
trellis GEMV and grouped-MoE kernels, Hadamard rotations around each quantized linear, a
converter from its safetensors packs, and experts re-quantized either from the lossy NVFP4 words
or from a BF16 checkpoint we do not keep, while losing FP4 tensor-core prefill. Revisit only if
step 7 lands and 3-bit experts then become the largest remaining byte share.

Taken from it instead: 8-bit HyperConnection weights (7a does the down projection; the up
projection needs a K=320 FP8 GEMV — vcruz's simulation kept draft acceptance at int8 and int6,
collapsed it at int4), X925 pinning and dynamic draft length (section 8). Their round profile
agrees with step 6: fused MoE runs at 82% of spec bandwidth; the mixer and the ~110 small
linears are the slow parts.
